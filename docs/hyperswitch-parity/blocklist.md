## Not ported
Original gaps recorded 2026-11-19; current status of every bullet is in `## Implementation disposition` below.

- Fingerprinting/data-kind pipeline (`core/blocklist.rs:16-38`; `api_models:10-20`): C++ hashes the entire raw JSON body with a merchant-derived key (`cppm:886-896`) instead of extracting `data` and applying per-`BlocklistDataKind` fingerprinting (`fingerprint`, `card_bin`, `generic_card_bin`, `extended_card_bin`). No `generate_fingerprint`/`transformers` module ported (`core/blocklist.rs:4`).
- Transaction-type semantics (`api_models:36-43,106-127,130-148`): upstream enum constrains `payment`/`payout`, defaults to `payment`, handles legacy NULL namespaces, and `generic_card_bin` counts cover deprecated card-bin kinds. C++ treats transaction_type/data_kind as arbitrary strings (`model/blocklist.cppm:28-58`), records `tt=` in a description field (`cppm:85,1032-1042`), and has no legacy-NULL or coverage rules.
- Profile resolution (`routes:17-20,44,75-78,163,194-197,250-253,590-591`): upstream reads `X-Profile-Id`, defaults to merchant default profile, errors on multi-profile merchants without it, and scopes add/remove/count/lookup/export/clone; C++ `profile_id_of` never reads that header (`cppm:844-857`) and add/remove/count/lookup/toggle/batch/export ignore profile except as a string key in config rows/id.
- Batch CSV validation and worker (`routes:345-367`; `core/blocklist.rs:88-106`, submodule `batch`): 5 MiB multipart limit, `type,data,metadata,transaction_type` header, per-row validation, 100k row cap, and background job execution are absent. C++ counts `\n` bytes and stores a pending job (`cppm:385-403`).
- CSV export lifecycle (`core/blocklist.rs:140-149`, submodule `export`): no CSV file generation, storage, `expires_at` lifecycle, downloadable flag derivation, or short-lived signed `download_url`. C++ stores a JWT string in `download_url` (`cppm:552,1114-1116`).
- Profile-clone worker and ownership checks (`api_models:314-329`; `core/blocklist.rs:151-160`, submodule `clone`): upstream validates profiles belong to the merchant and clones entries per target via a background job; C++ only checks target non-empty/not-source and writes a pending job row (`cppm:605-648`); no 404 for foreign source/target profiles (`routes:596`).
- Count-by-length semantics (`api_models:121-127`): C++ buckets by fingerprint-id length from `record.get_name()` (`cppm:242`), not the data/BIN length, so `counts_by_length` is meaningless vs upstream.
- `server_wrap` middleware (`routes:38-66` etc.): upstream `Flow` instrumentation (`AddToBlocklist`, `DeleteFromBlocklist`, `ListBlocklist`, `GetBlocklistCount`, `LookupBlocklistEntry`, `BatchBlocklistUpload`, etc.), `LockAction::NotApplicable`, unified error mapping, and 202 statuses are replaced by manual authorize + own counters (`cppm:1134-1139`) and uniform 200 `send_json` (`cppm:1154-1166`).
- Feature gate (`app.rs:2053`): C++ registers blocklist routes unconditionally (`cppm:659-785`).
- Guard enforcement: upstream guard state affects payment-time blocking (`core/blocklist.rs:78-86`); C++ writes a `blocklist.guard:` config row (`cppm:344-354`) that no payment path reads.
