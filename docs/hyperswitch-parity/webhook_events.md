## In-process substitutes (upstream-identical behavior)

These reproduce upstream behavior with in-process components; they are recorded here as implementation notes, not differences.

- **Webhook trigger** — upstream `trigger_webhook_and_raise_event` (`core:431-435`, `:450-463`) is modeled by `EventBus::publish("webhook.delivery.retry")` and `WebhookDeliveryService::enqueue/attempt/retry` (`webhook_events.cppm:308-320`). Same ordering: publish, enqueue, attempt, retry, then re-fetch (`:322-339`).
- **Business profile** — upstream `find_business_profile_by_merchant_id_profile_id` / `get_outgoing_webhook_headers` (`core:30-53`, `:344-353`, `utils.rs:576-588`) are modeled by `ConfigStore` keys `business_profile/<id>` (`validate_profile :486-504`) and `webhook_sensitive_headers/<id>` (`sensitive_header_names :1209-1231`). Profile ownership and redaction semantics are upstream-identical.
- **Idempotent id** — upstream `get_idempotent_event_id` (`utils.rs:229-261`) is reproduced exactly: base64url-no-pad SHA-256 of `primary_object_id_event_type`, plus an 8-character suffix for manual/automatic retries (`:1263-1279`). Because `utils::Sha256` exposes only lowercase hex, the handler carries a standard SHA-256 implementation returning the raw digest (`:1294-1364`) and uses `app::crypto::Base64Url`.
- **Event id** — upstream `generate_time_ordered_id("evt")` (`utils.rs:256-261`) is reproduced as `evt_` + a time-ordered UUIDv7-simple id (`:1249-1260`), preserving the upstream prefix and ordering property.
- **Keystore/decryption** — upstream merchant keystore + `crypto::Aes` decryption (`core:30-53`, `:244-254`) is modeled by `key_store().get` (`:505-513`) and `AesWrap::decrypt` over the deterministic `enc1:` framing (`:515-542`). Plaintext rows pass through unchanged.

## Items with no upstream behavior

- **`id_base` path tolerance** — upstream mounts the four routes at exact paths (`routes/webhook_events.rs:18-178`, `app.rs:3398-3424`) and performs no segment skipping. The C++ helper (`:1407-1420`) skips literal `events`/`profile`/`list` prefixes so ids resolve under both mount forms. This is extra tolerance only: it cannot create a wire route, cannot change a matched verb or response, and is harmless to parity. Verdict MATCH — no upstream behavior exists to mirror.
- **Build/module scaffolding** — module imports (`webhook_events.cppm:1-23`), the `app_dto:webhook_events` partition (`app/dto/webhook_events.cppm:1-9`) and route registration (`install :342-390`) are C++ build/wiring scaffolding with no wire surface. There is no upstream behavior to port for these; they are MATCH by absence of a wire contract.

## Typed DTO return type

`list_initial_delivery_attempts` and `list_generic` return the real typed DTO `app::dto::webhook_events::EventListResult` (`app/dto/webhook_events.cppm:248-258`), with getters/setters and a `serde::Serializable` specialization (`:317-327`). The handler imports it through a single alias (`webhook_events.cppm:438`) and no longer carries a local ad-hoc return-type struct; the two list handlers copy its typed items and separate COUNT into `TotalEventsResponse` (`:76-78`, `:133-135`, `:1046-1048`).

## Shared-module notes (informational)

These are optional follow-ups that could simplify the handler; none changes a verdict or wire behavior.

1. **`app::auth` granular permissions** — adding `ProfileWebhookEventRead`, `MerchantWebhookEventRead`, `MerchantWebhookEventWrite` plus connected/platform grant objects would let the handler drop its local typed rule (`:450-472`). The local `AppPermission::WEBHOOK_READ`/`WEBHOOK_WRITE` mapping produces the same authorization decision today.
2. **`app::store::webhook_events::WebhookEventRecord` rich domain fields** — columns for `business_profile_id`, `primary_object_id`, `initiator_merchant_id`, `initial_attempt_id`, `recipient`, `processor_merchant_id`, `request`, `response`, `delivery_attempt`, `is_webhook_notified`, `is_overall_delivery_successful` would remove the JSON field helpers (`payload_field :543-557`, `payload_bool :559-572`, `parse_headers :1158-1182`).
3. **`utils_hash` raw-digest helper** — exposing the raw 32-byte digest alongside the lowercase hex form would let the handler drop its local SHA-256 (`:1294-1364`). The current helper is a documented in-process implementation of the same algorithm.
4. **Business-profile service** — a real `find_business_profile_by_*` / `get_outgoing_webhook_headers` service would replace the `ConfigStore` keys used in `validate_profile :486-504` and `sensitive_header_names :1209-1231`.
5. **Webhook transport** — a live PSP/network delivery adapter would replace the deterministic `EventBus` + `WebhookDeliveryService` model (`:308-320`).
