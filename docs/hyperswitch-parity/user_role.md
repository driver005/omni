## Shared contract requests
These need changes outside the two files owned by this module; each is worked around locally and does not change route-level behaviour.

1. **`RoleRecord` schema fields** — upstream `diesel_models::role::Role` carries `groups`, `scope`, `merchant_product_type`; the local `app::store::roles::RoleRecord` (`include/app/store/identity_records.cppm:13-49`) has none of them. Custom-role metadata is kept in a cache side-store (`cppm:2390-2398,2401-2406`) keyed by `role_id`; adding those columns would let `role_info_from_id` read them exactly as upstream. `MerchantAccountRecord` also lacks `product_type`, so `merchant_product_type` (`cppm:2380-2387`) defaults to `Orchestration` as upstream does when the column is absent.
2. **Auth scheme types & token purpose** — upstream uses `JWTAuth{permission: MerchantUserRead|ProfileUserRead|ProfileUserWrite}`, `DashboardNoPermissionAuth`, `SinglePurposeJWTAuth(AcceptInvite)`, `SinglePurposeOrLoginTokenAuth(AcceptInvite)` and `Permission` enum (`user_role.rs(routes):33-37,54-57,269-272,293,335-339,493`). The handler uses `auth_rules().rule_for(operation)` plus JWT claim decoding (`cppm:2251-2271,2313-2320`). A shared `TokenPurpose`/`Permission` registry would let the harness enforce the exact scheme per route.
3. **Error wire names** — upstream `UserErrors` codes (`InvalidRoleId`, `InvalidRoleOperation`, `InvalidDeleteOperation`, `RoleNameAlreadyExists`, `RoleNameParsingError`, `MerchantIdNotFound`, `InvalidRoleOperationWithMessage`) map to the closest `core::error::AppErrorKind` (`NOT_FOUND`, `PRECONDITION_FAILED`, `ALREADY_EXISTS`, `VALIDATION_FAILED`, `FORBIDDEN`, `INTERNAL`) with the upstream code as message (`cppm:1147-1188,1270-1862`). Adding upstream error-code strings to the shared error envelope would make error bodies byte-identical.
4. **External infra substitutes** — Diesel `global_store`/`accounts_store` are represented by `AppRepository`/`Database`; merchant key-store decryption of names, the mail provider, and the business-profile service are represented by local repository/cache/event equivalents (`cppm:2380-2387,2600-2660,1842-1854`). Real adapters would remove these substitutes.
5. **Flow tracing spans** — upstream `api::server_wrap` + `Flow` emit tracing spans (`user_role.rs(routes):24,44,67,...`); the handler records per-op flow names + counters (`cppm:2322-2326`). Shared tracing middleware would close this gap.
6. **Feature gating & API locking** — upstream registers routes under specific `cfg` flags and passes `LockAction::NotApplicable` (`app.rs:2997,3184-3230`); no C++ feature-gate or API-lock concept is present in the handler layer (shared router/build concern).
