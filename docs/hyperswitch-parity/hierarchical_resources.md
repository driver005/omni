## Not ported
- Mandatory `X-Profile-Id` resolution/authorization: upstream extracts the header and fetches the profile scoped to the JWT merchant, treating `NotFound` as unauthorized (`routes/hierarchical_resources.rs:22-26`, `:28-46`, `:81-84`). C++ now fetches profile via repository and checks merchant (`cppm:553-572`), called in all four handlers (`:106/:194/:278/:364`).
- Real DB persistence of the `HierarchicalResource` entity — `insert_linked_resource`, `find_linked_resource_by_id`, `update_linked_resource_data`, `list_linked_resources_by_scope_id_and_resource_type`, `find_resource_scope_id`: C++ now uses repository CRUD (`cppm:138-149`, `:204-239`, `:293`, `:374-471`); `data` is pipe-delimited (`:692-708`).
- Organization key store lifecycle — master key, AES-256 keygen, key-manager transfer, encrypted `MerchantKeyStore`: C++ `key_store().get/put` with AES-256 purpose labels (`cppm:653-679`); no `transfer_key_to_key_manager`.
- EC P-256 keypair + CSR generation and private-key encryption with the org key: uuid-derived key + `KeyedHasher` CSR (`cppm:125-131`), `AesWrap.encrypt` (`:130`). No openssl EC/X509Req.
- Certificate verification on upload — base64 DER decode, `X509::from_der`, cert/key match, CN parse, status→Active: keyed digest (`:229`), `extract_apple_merchant_id` `CN=` text parse (`:710-719`), status→active (`:234`); no DER/X.509 or cert/key match, but merchant identifier now reaches `display_data` (`:311-313`).
- `authorize_scope_id_belongs_to_org` exact scope-vs-organization check returning `AccessForbidden`: `scope_belongs_to_org` compares persisted scope against authoritative org from merchant account (`cppm:611-623`, `:584-609`), `FORBIDDEN` on mismatch (`:211-215`, `:379-383`).
- `fetch_requestor_account` strict merchant-scoped resolution for MCA/profile/merchant with `to_not_found_response` and V2 `NotSupported`: all three types resolved via repository entities with merchant checks + NOT_FOUND/FORBIDDEN (`cppm:398-438`); no V2 gating.
- `on_link` re-encryption and `link_hierarchical_resource_data_to_scope` account updates: `AesWrap` rewrap (`:443-444`), link record CRUD (`:446-471`), `config_store().put` + `events().publish` (`:473-477`); no `RequestorHierarchicalResourceUpdate` on account entity.
- `resolve_apple_pay_certificate_data` cascade and `is_linked` computation: `resolve_effective_resource_id` (`:763-781`) → `find_linked_resource` profile→merchant fallback (`:739-761`), `is_linked` at `:315-316`.
- Resource-status gating `is_linkable` (Active only): string `"active"` check gates list (`:300`) and link precondition `PRECONDITION_FAILED` (`:384-388`) — equivalent intent, different mechanism.
- Request-wrapper semantics — per-op `Flow`, `server_wrap`, `api_locking::LockAction`, structured `ApiErrorResponse`: flat permission check (`:536-550`) + `AppError` (`:867-886`); only `metrics().record_flow` names approximate the flow (`:118/:201/:285/:371`).
- Response id/date wire encoding: plain-string wire shapes (`:29-63`) and real `created_at` (`:846-849`) now match upstream; no `{"value":...}` wrap or hardcoded date remains.
- Feature gating `#[cfg(all(feature = "olap", feature = "v1"))]` and V1/V2 split: no C++ equivalent gating.
