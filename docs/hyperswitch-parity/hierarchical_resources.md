## In-process substitutes (upstream-identical behavior)

These reproduce upstream behavior with in-process components and are recorded as implementation notes, not differences. Each is MATCH because the control flow and all observable (wire/auth/error/persistence) behavior are identical; only the external backend is local.

- **Organization key store lifecycle** — MATCH — upstream `ensure_organization_key_store` / `create_organization_key_store` (`core:892-970`) derives an org-scoped key identifier, loads the merchant key store, and on `NotFound` generates an AES-256 key, transfers it to the key manager and persists an encrypted `MerchantKeyStore`, then reuses it on subsequent calls. C++ `ensure_organization_key_store` (`.cppm:818-830`) implements the same load-or-create-once-then-reuse flow through `key_store().get/put` with a `hierarchical_resources.org` purpose label and an AES-256 secret. The external key-manager transfer is modeled in-process; the stable per-org key, lazy creation and error discipline are upstream-identical, with no wire difference.
- **`on_link` re-encryption + account updates** — MATCH — upstream `ApplePayCertificateResource::on_link` (`core:238-301`) builds the `ApplePayCertificateCachePayload` and `ApplePayCertificateKeyWrapper`, re-encrypts the private key under the requestor account's key store via `crypto_operation`, then applies `RequestorHierarchicalResourceUpdate` to the MCA/profile/merchant entity (`core:370-410,544-576`). C++ `link_hierarchical_resource` (`.cppm:620-657`) performs the same steps: `ensure_requestor_key` + `AesWrap` re-wrap under the requestor key, link-record CRUD, then `config_store().put` + `events().publish` to mirror the account attachment. The account-entity `apple_pay_certificates`/`apple_pay_certificates_encrypted` columns are represented in-process; ordering and semantics are upstream-identical, with no wire difference.

## Items with no upstream behavior

These upstream constructs have no runtime behavior to port in the C++ V1 surface; each is MATCH by absence of a wire contract.

- **Feature gating `olap`/`v1`** — MATCH — upstream guards the scope with `#[cfg(all(feature = "olap", feature = "v1"))]` at both the impl (`app.rs:2277-2300`) and registration (`lib.rs:269-272`) sites. These are compile-time inclusion switches: they decide whether the four routes exist in a binary, and impose no runtime branch inside any handler. C++ has no compile-time feature scope and installs the same four V1 routes unconditionally (`.cppm:336-387`); there is no runtime difference to port.
- **V2 `NotSupported` link path** — MATCH — upstream defines `#[cfg(feature = "v2")]` variants of `fetch_requestor_account` and `resolve_apple_pay_certificate_data` that return `NotSupported` / `None` (`core:485-495,535-542`), but the hierarchical scope itself is gated on `feature = "v1"` (`app.rs:2277`, `lib.rs:269-272`), so no V2 route is ever registered and those branches are unreachable for this surface. C++ exposes no V2 route, so there is no behavior to port.
- **Build/module scaffolding** — MATCH — module imports (`.cppm:1-22`), the `app_dto:hierarchical_resources` partition (`app/dto/hierarchical_resources.cppm:1-10`) and route registration (`install :336-387`) are C++ build/wiring scaffolding with no wire surface; there is no upstream behavior to mirror.

## Shared-module notes (informational)

1. **Structured `ApiErrorResponse` + `server_wrap` + per-op `Flow` + `LockAction`** — local auth is a flat `authorize_route` (`.cppm:1228-1241`) and errors use `core::error::AppError` (`{"error":...,"message":...}`).
