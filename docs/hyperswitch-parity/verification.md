## Not ported
- Route scope mismatch: upstream scopes are `/verify` and `/v2/verify` (`app.rs:2870,2886`); C++ mounts all four routes under `/verification` (`verification.cppm:231`), producing paths like `/verification/verify/apple_pay/:merchant_id`.
- Merchant key store load via master key `get_merchant_key_store_by_merchant_id` and MCA decryption with `key_store`: `core/verification/utils.rs:27-32,35-50`. C++ reads the MCA directly with no key store (`verification.cppm:84-89`).
- Profile-id validation `validate_profile_id_from_auth_layer` against the MCA: `core/verification/utils.rs:52-57`. Absent in C++ (no profile handling at all).
- Real Apple domain-registration HTTP call: cert + cert-key from config, `applepay_endpoint`, `add_certificate`/`add_certificate_key`, `call_connector_api`, and error logging: `core/verification.rs:26-63`. Replaced by a HMAC over a derived signing seed + connector `authorize` whose result is discarded (`verification.cppm:95-135`) — the comment at `:103-104` concedes this is a stand-in.
- Config-derived identifiers: upstream `encrypt_to` and `partner_internal_merchant_identifier` come from `applepay_merchant_configs.common_merchant_identifier` (`core/verification.rs:28-40`); C++ hardcodes both to `"Applepay_merchant"` (`verification.cppm:98-100`), conflating them with `partner_merchant_name`.
- Connector-error handling: upstream returns `InvalidRequestData{"Applepay verification Failed"}` on a non-`Ok` connector response and only updates the MCA on success (`core/verification.rs:65-92`). C++ ignores `connector_response` and always persists + returns `"Applepay verification Completed"` (`verification.cppm:133-153`).
- API-key auth branch: upstream `auth_type` accepts either API key (`HeaderAuth`/`V2ApiKeyAuth`) or JWT (`verification.rs:43-54,92-103,119-128,158-166`); C++ only builds a JWT rule (`verification.cppm:31-36,162-167`).
- Upstream `LockAction::NotApplicable`, `Flow::Verification` instrumentation, and `server_wrap` error mapping on every route (`verification.rs:12,21,55-56,109,130,167-168`); C++ uses flat authorization + custom `send_error` (`verification.cppm:37-40,284-295`) and adds its own cache/metrics instead (`verification.cppm:121-125,147-148,214-219`).
- Strict query requirement: upstream `ApplepayGetVerifiedDomainsParam` requires both `merchant_id` and `merchant_connector_account_id` (`api_models/verifications.rs:28-34`); C++ allows a missing MCA id and scans all merchant connectors (`verification.cppm:200-212`), behavior upstream does not expose.

## Implementation disposition
Disposition of each original `## Not ported` bullet against the current handler.

- Route scope mismatch — IMPLEMENTED — routes now mount `/verify` and `/v2/verify` with matching sub-paths (`verification.cppm:343,368`); the extra `/verification` prefix is gone.
- Merchant key store load via master key — SUBSTITUTED — resolves a signing seed via `secret_resolver().resolve("merchant_key_store", merchant_id)` then `key_store().get(...)`, with merchant-account hash-key/publishable-key and connector-detail fallbacks; no master-key load or MCA decryption (MCA records are plaintext in this port) (`verification.cppm:182-207`).
- Profile-id validation — IMPLEMENTED — `validate_profile_id` compares the authenticated profile id to the MCA profile id on both handlers (`verification.cppm:150-153,316-319,451-463`).
- Real Apple domain-registration HTTP call — DEFERRED — still a HMAC signature stand-in fed by config endpoint/cert refs plus connector `authorize`; requires external Apple gateway + PEM material. Stand-in conceded in comments (`verification.cppm:168-180,209-223`, STUB note at `:171,209`).
- Config-derived identifiers — IMPLEMENTED — `encrypt_to` and `partner_internal_merchant_identifier` are read from `applepay_merchant_configs.common_merchant_identifier` with `"Applepay_merchant"` fallback, no longer hardcoded (`verification.cppm:155-165`).
- Connector-error handling — IMPLEMENTED — a non-Ok connector status returns `InvalidRequestData{"Applepay verification Failed"}` and skips the MCA update; persistence happens only on success (`verification.cppm:225-253`).
- API-key auth branch — SUBSTITUTED — `auth_rules().rule_for(operation)` supplies the authoritative (API-key-capable) primary rule with a JWT fallback rule built from it; no explicit per-version `auth_type` branch (`verification.cppm:426-448`).
- `LockAction::NotApplicable` / `Flow::Verification` / `server_wrap` instrumentation — SUBSTITUTED — no lock acquired (NotApplicable), flat authorization + custom `send_error`, with local cache markers and `metrics()` flow/counter recording as the tracing substitute (`verification.cppm:220-223,255-261,322-329,399-410`).
- Strict query requirement — IMPLEMENTED — both `merchant_id` and `merchant_connector_account_id` are required; a missing field returns INVALID_REQUEST and the merchant-wide MCA scan was removed (`verification.cppm:281-296`).
