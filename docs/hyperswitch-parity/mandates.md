## Not ported
- Connector-side revoke chain: `get_profile_id_for_mandate` → `get_merchant_connector_account` → `ConnectorData::get_connector_by_name` → `construct_mandate_revoke_router_data` → `execute_connector_processing_step(CallConnectorAction::Trigger)` → `MandateUpdate::StatusUpdate{Revoked}` → `ExternalConnectorError` on failure (`core/mandate.rs:80-156`; `core/mandate/helpers.rs:14-44`; `core/mandate/utils.rs:19-104`). C++ revoke has zero connector interaction (`mandates.cppm:124-140`).
- Revocable-status state machine: upstream only attempts revoke for `Active | Inactive | Pending` and rejects `Revoked` with `MandateValidationFailed` (`core/mandate.rs:76-79,158-163`). C++ compares raw string `"revoked"` and errors `PRECONDITION_FAILED` (`mandates.cppm:118-122`); no enum, other statuses not distinguished.
- Key-store decryption / full response mapping: `MandateResponse::from_db_mandate` clones processor key store and populates `card` (last4, isin, network, fingerprint, etc.) and `customer_acceptance` (`core/mandate.rs:49-56,416-423`; `api_models/mandates.rs:79-85,88-137`). C++ `to_response` omits both fields (`mandates.cppm:296-338`).
- `created_time`, `created_time.lt/gt/lte/gte` query filters defined in upstream DTO and applied in DB `find_mandates_by_merchant_id` (`api_models/mandates.rs:155-178`; `core/mandate.rs:409-415`; `routes/mandates.rs:74`). C++ reads them then explicitly discards (`mandates.cppm:164-168`).
- List response shape: upstream returns bare `ApplicationResponse::Json(mandates_list)` (`core/mandate.rs:425`); C++ wraps in `{"data":[...],"count":...,"total_count":...}` (`mandates.cppm:213-216`).
- Platform/processor account + `storage_scheme` + key-store scoping on every lookup (`core/mandate.rs:42-46,69-75,410-413`). C++ instead scopes by `x-merchant-id` header or auth merchant id (`mandates.cppm:46-48,98-100,171-176`).
- Upstream auth flags: `allow_connected_scope_operation:false`, `allow_platform_self_operation:false`, JWT `Permission::MerchantMandateRead` with `allow_connected:false`/`allow_platform:false` (`routes/mandates.rs:33-36,61-64,86-97`). C++ uses only generic `PAYMENT_READ`/`PAYMENT_WRITE` (`mandates.cppm:29-32,81-84,149-152`).
- `GET /customers/{customer_id}/mandates` (OLAP): `customers::get_customer_mandates` → `core::mandate::get_customer_mandates` returning `Vec<MandateResponse>` or `MandateNotFound` when empty (`app.rs:1599-1600`; `routes/mandates.rs:6`; `core/mandate.rs:223-261`). Not registered in the C++ mandates handler (`mandates.cppm:219-257`).
- Internal mandate lifecycle helpers not exposed as routes: `update_connector_mandate_id` (connector_mandate_id backfill, only when existing is `None`) and `mandate_procedure` (SingleUse → Revoked, MultiUse → `CaptureAmountUpdate`, subsequent-payment metrics), plus validation `get_mandate_type` (`core/mandate.rs:168-220,275-401`; `core/mandate/helpers.rs:46-85`).
