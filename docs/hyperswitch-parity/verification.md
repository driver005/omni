## Implementation disposition
Disposition of each original `## Not ported` bullet against the current handler.

- Route scope mismatch — IMPLEMENTED — scopes are `/verify` and `/v2/verify` with the upstream sub-paths; no extra `/verification` prefix and no C++-only routes (`verification.cppm:276-324`; `app.rs:2870,2886`).
- Merchant key store load via master key + MCA decryption — IMPLEMENTED — `load_merchant_key_store` resolves the master key from KeyStore → secret resolver → config → deterministic default and derives the merchant key; `get_apple_pay_merchant_connector_account` checks the merchant account, loads the key store, looks up the MCA, and decrypts its details with `AesWrap` on read (`verification.cppm:425-457,538-569`; upstream `utils.rs:18-63`). Local in-process substitute: no external KMS; plaintext (unmarked) values pass through unchanged, `enc:`-marked values are unwrapped and re-wrapped on update (`:450-456,477-484`).
- Profile-id validation — IMPLEMENTED — `validate_profile_id_from_auth_layer` reproduces all three upstream arms with the exact `PreconditionFailed` messages (`:443-448,509-534`; upstream `core/utils.rs:2889-2911`).
- Real Apple domain-registration HTTP call — IMPLEMENTED (local in-process transport) — `request_builder` assembles the exact POST + `application/json` + cert/cert-key request, and `call_connector_api` performs the call through the in-process connector with the upstream two-level outcome (`TRANSPORT_ERROR` / `CONNECTOR_ERROR` / `SUCCESS`) and Ok/Err handling (`:363-392,571-636`; upstream `core/verification.rs:43-92`). No HMAC signature stand-in remains; cert/cert-key are carried on the request object and consumed only as non-secret transport metadata.
- Config-derived identifiers — IMPLEMENTED — `encrypt_to` and `partner_internal_merchant_identifier` come from `applepay_merchant_configs.common_merchant_identifier`, `partner_merchant_name` is the upstream constant `Applepay_merchant` (`:351-361`; upstream `core/verification.rs:9,26-41`).
- Connector-error handling — IMPLEMENTED — outer client error → `InternalServerError` (`:372-376`), inner non-Ok response → `INVALID_REQUEST` with exact `"Applepay verification Failed"` message (`:378-382`), MCA update only on the Ok branch (`:384-391`); the original error is recorded by `log_applepay_verification_response_if_error` (`:497-507`; upstream `core/verification.rs:65-92`, `utils.rs:138-148`).
- API-key auth branch — IMPLEMENTED — `authorize_verification` branches on `is_jwt_auth` (Bearer): JWT rule with the upstream permission/flags, otherwise v1 `API_KEY` / v2 `V2_API_KEY` with connected-scope and platform-self denied; the api-key header is carried as the local authorizer credential when no Bearer token is present (`:640-692`; upstream `routes/verification.rs:43-54,92-103,119-128,158-166`, `authentication.rs:6464-6475,6116-6124`).
- `LockAction::NotApplicable` / `Flow::Verification` / `server_wrap` instrumentation — IMPLEMENTED — no lock is acquired; `server_wrap` merchant match → `Unauthorized` (`:181-188,251-255`); `Flow::Verification` is recorded via `record_flow("Verification")` (`:215-216,267`); error mapping uses the exact upstream `AppErrorKind`/messages through `upstream_error`/`send_error` (`:712-731`). The old ephemeral cache markers were removed as C++-only artifacts.
- Strict query requirement — IMPLEMENTED — both `merchant_id` and `merchant_connector_account_id` are required; no header fallback or merchant-wide MCA scan (`:235-249`).

## Shared contract requests
These are outside this module's exclusive edit set and are needed only to remove the remaining *infrastructure* abstraction gaps (behavior is already upstream-identical locally):

- `app/auth`: expose merchant account type (standard / connected / platform) plus explicit `allow_connected_scope_operation` and `allow_platform_self_operation` flags on `RouteAuthRule` so the API-key branch can enforce `check_merchant_access` (`authentication.rs:6487-6509`) without the local connected-header check at `verification.cppm:658-662`.
- `app/connector`: expose a generic `call_connector_api(state, request, operation, …)` returning a two-level result, so `verification.cppm:603-636` can delegate the transport shape instead of reconstructing it from `IConnector::authorize`.
- `app/keystore` / `app/context`: provide a configured store master key accessor (`get_master_key`) so `load_merchant_key_store` (`verification.cppm:540-557`) need not fall back to KeyStore/secret-resolver/config defaults.
