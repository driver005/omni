## Upstream helper ownership (category c — verified from upstream, not assumed)
The three token-lifecycle helpers in `core/external_service_auth.rs` are wired in upstream — to a **different domain**. Verification:

- `core/external_service_auth.rs:24` `generate_external_token` → called only at `routes/hypersense.rs:22` (`get_hypersense_token`), mounted at `GET /hypersense/token` (`app.rs:2020-2021`).
- `core/external_service_auth.rs:51` `signout_external_token` → called only at `routes/hypersense.rs:49` (`signout_hypersense_token`), mounted at `POST /hypersense/signout` (`app.rs:2028-2029`).
- `core/external_service_auth.rs:66` `verify_external_token` → called only at `routes/hypersense.rs:69` (`verify_hypersense_token`), mounted at `POST /hypersense/verify_token` (`app.rs:2024-2025`).
- A whole-repo search for these symbols finds only their definitions and the three `routes/hypersense.rs` call sites — no call site in `routes/external_service_auth.rs` or the `/external-service` scope (`app.rs:2000-2011`).

Consequence: there is no `external_service_auth`-domain route behavior to port for them; the `Hypersense` response arm they produce is the separate hypersense domain's concern (its C++ handler is `include/app/handlers/hypersense.cppm`). This module therefore has **no behavior to port** for those helpers, which resolves those items to MATCH without adding any C++ route.
