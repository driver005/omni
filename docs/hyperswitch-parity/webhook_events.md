## Shared contract requests

These are genuinely shared-module dependencies that cannot be closed inside this handler alone. They do not change the four MATCH verdicts because the handler implements the upstream logic locally with in-process substitutes.

1. **`app::auth` granular permissions** — add `ProfileWebhookEventRead`, `MerchantWebhookEventRead`, `MerchantWebhookEventWrite` to the permission/JWTAuth model plus connected/platform grant objects. Handler currently maps them to `AppPermission::WEBHOOK_READ`/`WEBHOOK_WRITE` via a local typed rule (`webhook_events.cppm:450-471`).
2. **`app::store::webhook_events::WebhookEventRecord` rich domain fields** — add `business_profile_id`, `primary_object_id`, `initiator_merchant_id`, `initial_attempt_id`, `recipient`, `processor_merchant_id`, `request`, `response`, `delivery_attempt`, `is_webhook_notified`, `is_overall_delivery_successful` columns so the handler can stop scraping the JSON `payload` string (`payload_field`, `payload_bool`, `parse_headers` at `:543-570`, `:1158-1207`).
3. **`utils_hash` raw-digest + base64url-no-pad helper** — `utils::Sha256` currently exposes only lowercase hex (`include/utils/hash/sha256.cppm`); upstream `get_idempotent_event_id` base64url-encodes the raw 32-byte digest. Handler carries a local SHA-256 implementation (`:1294-1348`) and uses `app::crypto::Base64Url` because adding a `utils_hash` dep would require editing the shared `BUILD.bazel`.
4. **Business-profile service** — `ConfigStore` keys `business_profile/<id>` and `webhook_sensitive_headers/<id>` stand in for `find_business_profile_by_*` and `get_outgoing_webhook_headers` (`validate_profile` `:486-503`, `sensitive_header_names` `:1209-1230`). A real business-profile store would remove these substitutes.
5. **Webhook trigger semantics** — `EventBus::publish` + `WebhookDeliveryService` deterministically model `trigger_webhook_and_raise_event` (`:309-321`); real PSP/network delivery is out of scope for in-process parity.
