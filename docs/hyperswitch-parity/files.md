## Implementation disposition (exact upstream control flow; local backend substitutes)

- Multipart request parsing — IMPLEMENTED — `get_create_file_request` (`.cppm:711-777` ← `transformers.rs:13-82`) decodes the `purpose`, `file` (filename + bytes), and `dispute_id` parts from the raw body via a local `multipart/form-data` parser (`:797-858`); file size is `i32::try_from(file.len())`, empty file is `MissingFile`, and the mime is sniffed from magic bytes (`:936-972` ← `infer::get` at `transformers.rs:68`). `read_string`/`get_file_purpose` at `:780-794` ← `helpers.rs:17-32`.
- File validation `validate_file_upload` — IMPLEMENTED — `.cppm:444-492` ← `helpers.rs:34-86`: missing dispute id, processor-scoped dispute lookup (`find_dispute`, `:1042-1057`), connector-by-name (`:1060-1082`) and `Connector.validate_file_upload` substitute (`check_feature_matrix`, `:470-485`) with upstream messages `Dispute id not found in the request`, `Dispute does not exist in our records`, `File validation failed {reason}`.
- ID generation `generate_id(consts::ID_LENGTH=20, "file")` — IMPLEMENTED — `.cppm:1180-1185` ← `common_utils/lib.rs:626-628`; `file_` + 20-char suffix, duplicate insert guarded by `repository().create_file` (`repository.cppm:1209`).
- DB persistence — IMPLEMENTED — `insert_file_metadata`/`update_file_metadata` (`.cppm:977-990` ← `core/files.rs:35-86`) with `UNAVAILABLE -> AVAILABLE`, provider file id, snake_case upload provider and profile id; row removal at `:388-391` ← `core/files.rs:98-107`.
- Upload pipeline `upload_and_get_provider_provider_file_id_profile_id` — IMPLEMENTED (local connector/S3 backends) — `.cppm:497-572` ← `helpers.rs:287-406`: dispute lookup, `supports_file_storage_module` on the dispute connector (`:1173-1177` ← `connector_enums.rs:356-358`), payment-intent + payment-attempt lookups (`:1086-1114`), connector upload via `submit_evidence` (`:535-559`) or `file_storage_client.upload_file` substitute keyed by `file_key = "{merchant_id}/{file_id}"` (`:564`, `:1026-1029`), returning `(provider_file_id, provider, profile_id, merchant_connector_id)`.

## Shared contract requests
Framework/shared items that cannot be delivered by edits to this module's exclusive files; local workarounds are in place and do not change route-observable behavior.

1. **Structured `ApiErrorResponse` + `server_wrap` + dual `auth_type` extractor (`ApiKeyAuth` + `DashboardNoPermissionAuth`)**: local auth is a single API-key `authorize_route` (`.cppm:1208-1220`) and errors use `core::error::AppError` (`{"error":...,"message":...}`). Request shared support in `app/auth`, `core/error`, `app/services` for the upstream `ApiErrorResponse` envelope, the `x-api-key` claim path, and the Dashboard-no-permission fallback. Workaround: exact upstream flags on the local rule + verbatim upstream error messages.
2. **`file_storage_client` (S3) object store**: request a shared local object-store service in `app/services` exposing `upload_file/retrieve_file/delete_file` keyed by the upstream `file_key`/`provider_file_id`. Workaround: `config_store` namespace `file_storage` (`.cppm:1026-1039`).
3. **Typed connector `FileUpload`/`RetrieveFile` interfaces and named-connector resolution**: request `hyperswitch_interfaces`-equivalent `Upload`/`Retrieve` traits and a public `ConnectorRouter::find_by_name` in `app/connector`. Workaround: `ConnectorRequest` operations `validate_file_upload`, `upload_file`/`submit_evidence`, `retrieve_file` driven by `check_feature_matrix` (`.cppm:470-485,535-559,685-696`) and merchant-based selection with a metric-marked fallback (`:1060-1082`).
4. **Platform identity + full file-metadata columns**: request `platform.get_processor()/get_provider()` resolution and `processor_merchant_id`, `merchant_connector_id`, `connector_label` columns on `FileRecord` (`app/store`) plus `profile_id` on `PaymentIntentRecord` and `attempt_id` on `DisputeRecord`. Workaround: header/auth merchant id (`.cppm:1224-1231`), dispute profile id (`:554-558`) and MCA lookup from merchant connectors (`:1117-1133`).
5. **Feature gating `olap`/`v1`**: C++ has no compile-time feature scope; the three V1 files routes are always installed (`.cppm:245-286`). No runtime difference for the V1 surface.
