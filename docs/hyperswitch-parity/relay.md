## In-process equivalents (upstream-identical behavior)
- Diesel DB interfaces (`insert_relay`/`update_relay`/`find_relay_by_id`) and the accounts/profiles store are represented by `app::store::relay_records`, `config_store` and `superposition()`; all upstream-visible CRUD, 404 semantics and profile resolution are preserved (`relay.cppm:142-151,375-383,495-530,1572-1584`).
- The processor key store is `app::keystore` (`key_store().get`, `relay.cppm:130,926`); credentials are resolved but kept out of persisted payloads/logs (`:136-138`).
- Connector-specific webhook decoding/gateway and `call_connector_api` transport are replaced by `decode_relay_webhook` + `IConnector` methods and process trackers (`relay.cppm:974-1044,1528-1561`), with the same status mapping (`relay_status_for_event` `:1046-1055`) and force-sync gate (`:1090-1143`).
- Rust type machinery (`RelayInterface` trait, four `RelayRequestInner<T>` impls, domain `relay::Relay`, `ForeignTryFrom`) is a real local port plus the typed response DTO; wire-visible validation, ids, statuses, data and errors are identical (R1, R2, R9).
- v1/v2 `#[cfg]` branches are runtime `feature_enabled` checks (`relay.cppm:89,276,425,1473-1478`); `#[cfg(feature = "oltp")]` route gating is build scaffolding with no request-time behavior to port — the C++ routes are registered unconditionally (`relay.cppm:742-798`).
- `server_wrap` `LockAction::NotApplicable` means no lock is acquired upstream; the C++ handler records the flow metric and consults the lock registry without acquiring (`relay.cppm:1519-1526,663-665`). No lock semantics to reproduce.
