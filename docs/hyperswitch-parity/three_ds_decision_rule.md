These need changes outside the two files owned by this module; each is worked around locally and does not change route-level behavior.

1. **Euclid VM / DSL engine** — upstream `backend::VirInterpreterBackend::with_program(program).execute(backend_input)` (`core.rs:67-75`, `crates/euclid`) is an external Rust VM with no C++ port. `evaluate_upstream_program` (`three_ds_decision_rule.cppm:577-633`) reads the same stored `Program<ThreeDSDecisionRule>` wire shape and evaluates the same comparison operators (`equal/not_equal/less_than/less_than_equal/greater_than/greater_than_equal`, enum/number/metadata variants and arrays) over the full `BackendInput`. A shared in-process Euclid interpreter would remove the substitute; the decision wire shape and all input fields are already faithful.
2. **Exact repository lookup + `Platform`** — upstream `find_routing_algorithm_by_algorithm_id_processor_merchant_id(routing_id, processor_merchant_id)` (`core.rs:48-54`) has no local equivalent; the local store exposes `find_routing_config_by_string` plus merchant checks (`three_ds_decision_rule.cppm:767-771`) and `app::store::routing::RoutingConfigRecord`. A repo method keyed by `(algorithm_id, merchant_id)` and a local `Platform`/processor-account model would make the persistence read byte-identical. Merchant id is already derived from the authenticated identity.
3. **Auth registry row** — `include/app/auth/registry.cppm:120` records `execute_decision_rule` as `API_KEY, PAYMENT_WRITE, allow_connected=true, allow_platform=true`, whereas upstream uses `ApiKeyAuth{allow_connected_scope_operation:false, allow_platform_self_operation:false}` with no route-level permission. For API_KEY the two flags are ignored by `authorize_route`, and `PAYMENT_WRITE` only narrows when a `permission` claim is present, so route behavior matches; correcting the row to `false,false` and a permissionless API-key rule would make the evidence exact.
4. **serde `deny_unknown_fields`** — upstream request DTO rejects unknown fields (`api_models/...:68`); C++ `FieldOptions{}` descriptors (`dto/three_ds_decision_rule.cppm:273-288`) do not. A framework-level strictness flag would close the input-validation gap without changing the handler.
5. **Observability** — upstream `#[instrument(... Flow::ThreeDsDecisionRuleExecute)]` and `ApiEventMetric` events (`routes:10`, `api_models/...:95-105`); local uses `record_flow` + a counter (`three_ds_decision_rule.cppm:700-702`). Router/build-layer concern.
6. **Compile-time gating / locking** — upstream registers the route under `#[cfg(feature = "oltp")]` with `LockAction::NotApplicable` (`app.rs:2839-2848`, `routes:31`); no C++ feature-gate/API-lock concept exists in the handler layer.
